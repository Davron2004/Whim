## #181: a background agent waits for ever at an approval prompt
Facts: harness.md §11 (lines ~379-380) already says a `running` tool call with no output may be waiting on approval and to interrupt before retrying; `implementer.md` and `fix-worker.md` do not name the forms that prompt; a sub-orchestrator cannot `TaskStop` a child it does not own. Unverified: whether a PreToolUse hook's input names the calling agent (needed for A).
- **A. Never ask in a subagent: the Bash policy hook denies instead of prompting.** `bash-policy.sh` (and `unroll-command.mjs`) already judge segment by segment. For a subagent session it would return `deny` with a one-line hint ("use Write/Edit, one simple command per call") for every verdict that would otherwise be `ask`. The agent gets an error in milliseconds and adapts; no prompt exists to wait on. Cost: an edit to `.claude/hooks` (CONFIG_SET, human-bootstrap) plus a hook test; depends on the hook seeing the agent identity or a dispatcher-set marker (e.g. env). Covers the whole class for hooked tools, not for prompts that come from the permission-mode layer.
- **B. Heartbeat file the dispatcher checks.** PreToolUse writes `.claude/run/inflight/<agent-id>` (tool name + start time), PostToolUse deletes it; the orchestrator's wait loop (and the `SubagentStop` gate) treats a file older than 10 minutes as "waiting on a prompt": abandon that worktree, create a new one, dispatch a fresh agent (never a second writer in the stalled tree). Detects, never unblocks; also covers non-hook prompts; leaves a zombie that only the top-level session can stop.
- **C. Doc and brief rule.** Name the prompting forms (heredocs, `$(...)`, `rm -rf`, `&`/`sleep`, inline interpreters, chained commands) and the reason in `implementer.md`, `fix-worker.md` and `brief-rules.md`; add to harness.md §11 what a sub-orchestrator that cannot stop the child does (new worktree, fresh agent, wake the PO). Zero risk, no CONFIG_SET beyond `.claude/agents` (which is in CONFIG_SET: human edit), but it only lowers the odds.
- **Recommendation: C now, plus A.** C is cheap and teaches the cause. A removes the failure mode instead of detecting it, which is what an unattended overnight run needs. Add B only if A's agent identity turns out to be unavailable (then B's file doubles as the identity). Do not plan the implementation until the PO picks.
