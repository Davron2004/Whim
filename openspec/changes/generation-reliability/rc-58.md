# rc-58 — root cause of "We couldn't verify this app ran safely" (#58), provider-failure evidence (#57/#66)

Investigated 2026-10-31 on `probe/rc-58` (based on 899a2bbc = main). Line numbers are at 899a2bbc.

## ROOT CAUSE (#58)

**It's a model fault that the harness mislabels as a harness fault.** When a candidate throws while
its module is being evaluated (top-level code, before any component renders), the throw aborts the
whole inline script that `wrappedBundleSource` built. So the trailing `window.__whimAfterBundle()`
call never runs (`src/runtime/web/loader.js:262-275`). That means no mount, no `paint` frame, and,
because the trusted probes only run after paint (`loader.js:192-202`), no `probes` frame. CDP still
records the throw as `runtime_throw`. `awaitMount` treats any diagnostic as "settled" and returns at
once (`synthrun/observe.ts:645`), and the run closes with `contained: null` plus
`containment_unobserved` (`synthrun/report.ts:200`, `observe.ts:332`). The run stage maps `null` to
the unobserved arm (`server/src/generation/stages/run.ts:75`), and the machine ends the run as
terminal `run_unverified` with no repair (`machine.ts:1203-1206`, `:622-626`). An ordinary
crash-on-load bug, which the repair loop would fix like any other `runtime_throw`, ends the build in
under a second. A throw during render, in an effect or in a rejected promise does **not** take this
path: paint still happens, the probes still report, and the run goes to repair as normal (repro
below).

**Confidence: high** that this is the mechanism and the only model-reachable path that ends in
about 0.1 s. **Medium** that both benchmark cases were specifically module-scope throws: their
candidates were never saved, and I didn't re-run the real models, because at a 2/100 rate the ~15
allowed generations would expect 0.3 hits. The other sub-second paths (table rows 3-6) need a runtime
or harness bug that nothing points to. Two of the seven real-model candidates checked in at
`synthrun/test/fixtures/flowbench-2026-10-09/` already run executable code at module scope (a
module-level `new Set(...)`), so models do write top-level code. One `new Intl.NumberFormat(…,
{style:'currency'})` without a currency code, or a hook called at module scope, is enough.

## RECOMMENDED FIX (#58)

1. **Server classification (the fix).** In `server/src/generation/stages/run.ts`, split "the verdict
   was never observed because the candidate never mounted" from "the verdict is missing for no
   candidate reason". If `contained === null` and the harness recorded a candidate-attributed cause
   (a CDP `runtime_throw`/`unhandled_rejection` from the candidate's anonymous script, a `[bundle]`
   error, or `mount_timeout`), return a new **repairable** arm. The machine then feeds those
   diagnostics (message, line and hint, exactly as a normal `runtime_throw` repair does, and never a
   `containment_*` detail) into the repair loop and spends one repair attempt. **Never deliver**: the
   repaired candidate gets its own fresh run and has to earn `contained:true`. Safety holds because
   path 1 never delivered anyway; the change only turns a dead end into a repair. This needs a
   MODIFIED delta to generation-pipeline "The run stage is the synthetic harness…" (scenarios "An
   unobserved verdict short-circuits with its own reason" and "…consumes no repair attempt") and to
   synthetic-run "An unobserved verdict is not a negative one". Wording: a candidate that crashed or
   hung before mount is a candidate fault, not an unverified run.
2. **Residual unobserved (rows 3-6, 8-9) = harness fault → re-run once.** Re-run the same candidate
   once in a fresh context before giving the terminal `run_unverified`. A harness fault doesn't
   depend on the candidate, so the once-only retry is bounded and can't launder anything: only an
   observed `true` ever delivers. This replaces design D3's "never re-run", so state that in the
   delta.
3. **Hardening, optional, needs a runtime change and the invariants suites.** Run the trusted probes
   even when the bundle fails to evaluate or mount: wrap the bundle in
   `try { … } finally { __whimAfterBundle() }`, and have its no-export and mount-error branches still
   call `trustedRunProbes`. Then a module-scope escape attempt that ends in a throw is caught as
   `containment_failed` instead of hiding behind "unverified". Touches loader.js and the
   spike2-constraints area, so it should be its own chain with `npm run invariants` +
   `bridge:invariants`.
4. **Log (issue ask).** Keep `machine.ts:767` and add a closed-vocabulary `phase` (or `where`) next
   to `check`: `module-eval | bundle | mount | deliver | probes | mount-timeout | none`. Derive it from
   the diagnostic's channel (CDP anonymous-script vs loader `where`), never from message text, and
   carry no message, source or symbol. Also log `rerun: true|false` for item 2.
5. **Regression tests (red before the fix):**
   - `server/test/e2e.ts`, real Chromium plus `ScriptedModelClient` (pattern: `rc58-repro.ts`
     `fullMachine`). Turns: plan, engineer = tip-splitter with a module-scope
     `new Intl.NumberFormat('en-US',{style:'currency'})`, repair = the honest tip-splitter. Assert a
     `repair` stage happened, the repair request's diagnostics include `runtime_throw`, and the
     terminal is `result`. Today: `failure` with `UNVERIFIED_RUN_REASON`, `attempts:1` (red, shown
     above).
   - `server/test/run-stage.suite.ts`: a `fakeReport({contained:null, diagnostics:[runtime_throw (candidate), containment_unobserved]})`
     maps to the repairable arm; `[containment_unobserved]` alone still maps to unobserved. Second
     test as a discriminating red-check: `[probes]` error only → not repairable.
   - The machine suite: residual unobserved re-runs exactly once, then ends terminal `run_unverified`
     with log `phase`/`rerun`.

**Production shows no upstream provider failure at all** (no 5xx, 429, stream or network error,
timeout or 402) in any generation stage. #57's evidence is benchmark-only
(`docs/research/generation-speed-2026-09.md`). Today a failed call logs only
`model call {role, model, provider?, ttftMs?, durationMs, outcome:"failed"}` (`openrouter.ts:408`),
with **no HTTP status or error kind**. The machine then logs `model turn retried {role, errorClass, restart}`
(`machine.ts:802`) or `run failed {errorClass, detail, stack}` at error (`machine.ts:729`). A breaker
needs `status` and `errorKind` (`network|rate_limit|credit|…`) on the `model call` failed line,
which is where its consecutive-failure counter and the `breaker open`/`breaker closed` lines belong.

**What the app shows today when OpenRouter returns 5xx mid-generation (#66 "To check first"):** a
generate or repair turn that fails with 5xx, 429 or a network/stream error is resent once with the
same messages (`isUpstreamModelFailure`, `model.ts:91`; `machine.ts:796-803`, beta-1 D10). If tokens
had already streamed, the device gets `restart` first and voids them. If the resend fails too, or the
failing turn is `plan` (never resent), `endOnThrow` emits the terminal `failure` "Something went
wrong while I was making this app. Please try again." with ledger code `internal_error`
(`machine.ts:724-745`). The phone shows the Failure page ("Couldn't make this", that sentence, Try
again) with nothing saying the provider is at fault. Only a 402 gets its own copy
(`credit_exhausted`, "Whim has used up its budget…").
