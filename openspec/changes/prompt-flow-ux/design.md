# Design: prompt-flow-ux

## Context

The server side of this loop is fully built and stubbed (#8, `research.md` §Current behavior): `POST /v1/rewrite` (canned), `POST /v1/generate` (SSE over POST+fetch, a fixed `STUB_APP_RECORD` on success, a `[[fail]]`-triggered failure path, one terminal event always last), both gated on `x-whim-device`. Nothing on the device talks to it yet — the home screen's create tile is a stubbed placeholder, and two live decisions already commit this change to specific behavior: #48 D4 (write the `{v:1,text}` prompt envelope) and #52 D2 / the `linked-apps` spec (silently share storage on a rewind-continuation). This design wires the client end of that pipe against the *existing* stub contract; #11 swaps the server internals later without changing anything this change builds against.

## Goals / Non-Goals

**Goals**
- Prompt → rewrite preview → approve → SSE-driven generation → install/update, working end to end against the stub server.
- Fulfill #48 D4 (envelope) and #52 D2 (silent shared-storage continuation) exactly as those decisions already specify.
- New device-side modules (`generation-client.ts`, `device-id.ts`) that are Node-testable and injectable (mirroring the codebase's existing DI idioms — `DeleteStorage`, `KVBackend`, injectable clocks), so `npm run launcher:test` covers them without a real network or server process.
- Every new screen follows the launcher's established full-screen-sibling pattern (`shellPalette`, own `BackHandler`, `COPY` table, product-verbs guard).

**Non-Goals**
- Any change to `@whim/contract` or `@whim/server` — this change treats the stub pipeline as a black box and must keep working unmodified when #11 replaces its internals.
- Real rewrite/engineer model behavior, plan/check/repair semantics, prompt engineering — all #11.
- An in-app (running-mini-app) prompt entry point — `FloatingExit` today is a single tap that exits to home; adding a menu there is a separate, unrelated back-nav design question (#43b territory) this change does not reopen.
- Automatic LAN server discovery — v1 is personal/LAN-dev only; a manually entered address is sufficient and matches the roadmap's "no network capability, LAN dev only" framing.

## Decisions

**D1 — Screen union grows four variants, orchestration lives in `LauncherRoot`.** `Screen` gains `{kind:'prompt', editing?: InstalledApp}` | `{kind:'rewrite-preview', editing?: InstalledApp, originalPrompt: string, rewrittenPrompt: string}` | `{kind:'generating', editing?: InstalledApp, prompt: string, stage: GenerationEvent['stage'] | null}` | `{kind:'failure', editing?: InstalledApp, prompt: string, reason: string, diagnostics: readonly {hint:string}[]}`. `editing` absent = new-app flow (home tile); present = edit flow (per-app "Prompt again" row). New screen components (`PromptScreen`, `RewritePreviewScreen`, `GeneratingScreen`, `FailureScreen`) are presentational — the async SSE loop, abort wiring, and the install/update/fork decision (D5) live in `LauncherRoot`'s handlers, exactly like the existing `onFork`/`onDelete` async handlers. Rationale: keeps the four new components trivially testable/reviewable and matches the file's existing shape; the alternative (a dedicated orchestrator hook module) was considered and rejected as unwarranted ceremony for four sequential steps with no branching reuse elsewhere.

**D2 — `generation-client.ts`: a small, injectable SSE client, no new dependency.**
```
getDeviceId(kv: KVBackend): string                                   // read-or-generate-and-persist whim.device:v1
rewritePrompt(opts: ClientOptions, prompt: string): Promise<RewriteResponse>
generateApp(opts: ClientOptions, request: GenerateRequest, signal?: AbortSignal): AsyncIterable<GenerationEvent>
class GenerationClientError extends Error { kind: 'network'|'device_id'|'http'|'stream_parse'; status?: number; hint?: string }
interface ClientOptions { baseUrl: string; deviceId: string; fetchImpl?: typeof fetch }
```
`generateApp` parses the same `event:`/`data:`/`id:`/blank-line SSE framing the server writes (`server/src/sse.ts`) directly off the fetch `Response.body` reader — no `EventSource` (POST+body isn't representable in it, already noted in `contract/src/index.ts`). Frames are validated against `GenerationEvent` (zod, from `@whim/contract` — already a dependency, no new package) before being yielded; a frame that fails validation raises `GenerationClientError{kind:'stream_parse'}` rather than silently passing bad data to the UI. `fetchImpl` defaults to global `fetch` (RN 0.85 supports streaming response bodies) and is injectable so `launcher:test` can supply canned `Response` objects with no real HTTP server — mirrors `server/test/sse-reader.ts`'s parsing idiom but as production, not test, code, and inverted (server writes frames, this reads them). `getDeviceId` generates a UUID-v4-*shaped* string via `Math.random` (feature-detecting `globalThis.crypto?.randomUUID` first) — this identifier is anonymous metering, not a security boundary, so a non-cryptographic fallback is acceptable and avoids adding `react-native-get-random-values`/`uuid` (which would touch the protected `package.json`). Alternative (add the dependency) rejected: forces a HUMAN-BOOTSTRAP chain for a one-line generator.

**D3 — Server address is a manually entered Settings field, persisted like the theme pref.** `SettingsScreen.tsx` gains a text field (`whim.server-url:v1` in the same `whim.launcher` KVBackend, sanitized like `ThemePref` — invalid/absent falls back to `undefined`, never throws). The prompt screen reads it via the same `useTheme()`-style context/prop plumbing already in `LauncherRoot`; if unset, submitting a prompt shows an honest inline message ("Set your server's address in Settings") rather than a network error. Alternative (bake a build-time env var via `react-native-config`) rejected: new native dependency and build-config surface, disproportionate for a LAN-dev-only v1 feature that one person configures once.

**D4 — Rewrite preview shows only the rewritten text; the user edits that text directly.** No separate "intent" vs. "SDK-detail" split (§10.1's later, post-v1 control-modes distinction) — v1's rewrite is one plain-English string end to end (confirmed by the current canned server behavior, which is itself plain-English), so the preview screen is a single editable `TextInput` seeded with `rewrittenPrompt`, with the original prompt shown small/muted above it for context. Approving sends the (possibly user-edited) text as `GenerateRequest.prompt`.

**D5 — Delivery: tip detection decides install vs. update vs. silent-fork-continuation.** On `result`:
1. **New app** (`editing` absent): `access.install({id: <fresh id>, name: <derived>, record: <mapped from wire>, bundleSource: wire.bundle, prompt: envelope(text), example: false})`. Navigate to `{kind:'app', ...}` for the new entry.
2. **Edit, at tip** (`editing` present and `isAtTip(access, editing)` true — D6): `access.update(editing, {record, bundleSource: wire.bundle, schemaJson: JSON.stringify(wire.schema), prompt: envelope(text)})`. Same entry, new snapshot on its existing lineage. Navigate to `{kind:'app', ...}` for `editing`.
3. **Edit, behind tip / continuation** (`editing` present, not at tip — the user restored an old version via History, then re-prompted): `const fork = await access.fork(editing, undefined, {shareData:true})` (no share/fresh question — decision #52 D2, `linked-apps` spec "Rewind continuations share by default"), then `access.update(fork, {record, bundleSource: wire.bundle, schemaJson, prompt: envelope(text)})`. Navigate to `{kind:'app', ...}` for the new `fork` entry — a brand-new tile appears on Home, sharing the original's data.
`envelope(text)` = `JSON.stringify({v:1, text})`, matching `parsePromptEnvelope`'s expected shape (`prompt-envelope.ts`, unchanged). `GenerateRequest.app` (for cases 2 and 3) is built from `editing`'s *current active* snapshot: `{source: await access.activeSource(editing) /* new, see D7 */, manifest: editing.record.manifest, schema: editing.record.schemaArtifact ?? {}}`.

**D6 — `isAtTip` lives in `history-logic.ts`, reusing the existing F1-safe listing split.** `export async function isAtTip(access: StoreAccess, app: InstalledApp): Promise<boolean> { const list = await listVersions(access, app); const active = await access.activeId(app); return list[0]?.id === active; }`. This reuses `listVersions`'s existing fork-vs-original branching (`history()` for forks, `timeline()` for originals — the same F1 DAG-ambiguity guard #6 already ships and tests), rather than inventing a second, differently-buggy tip check. "At tip" is defined operationally as "matches what the History screen's own top row would show as current" — the same definition the user already sees.

**D7 — `StoreAccess` gains `update()` and an `activeSource` read; `install` and `update` both write `schema.json`.** `update(entry, {record, bundleSource, schemaJson?, prompt}): Promise<InstalledApp>` — `ensureLineage`, `store.snapshot(storeIdOf(entry), {'bundle.js': bundleSource, ...(schemaJson ? {'schema.json': schemaJson} : {})}, prompt)`, then `index.put({...entry, record})` (name/createdAt/id/lineage unchanged). `install`'s `InstallSpec` gains the same optional `schemaJson?: string`, written alongside `bundle.js` — this is the change that makes #6's dormant `history-logic.ts` schema-diff annotation feature non-vacuous for the first time (no #6 behavior change; its annotation logic is untouched, only its input stops being permanently absent). `activeSource(entry): Promise<string>` mirrors `activeBundle` but reads the `bundle.js` artifact's *source* — actually the same artifact today (the store is a flat `Record<string,string>` of tracked files; the wire's `source`/`bundle` distinction has no on-disk counterpart yet since only `bundle.js` is tracked). Recorded as a known limitation (D8's risk row): v1's edit flow re-sends the compiled bundle text as `GenerateRequest.app.source`, not original TypeScript, because no snapshot has ever tracked source separately. This is honest given the wire type only requires a string and the stub pipeline does not interpret it; #11 (whose `Pipeline` will actually read `app.source`) is expected to either track a `source.ts` artifact by then or accept this — noted as a roadmap contract note in tasks.md, not resolved here.

## Risks / Trade-offs

- [Non-cryptographic device UUID] → not a security boundary (anonymous metering only, same pattern the server already treats as untrusted-by-design — `x-whim-device` is validated only as UUID-*shaped*, never authenticated); avoids a protected-file (`package.json`) dependency edit.
- [Manual server-address entry is friction] → acceptable for v1's explicitly LAN-dev/personal-use scope (roadmap "What v1 means"); revisit if/when a real deployment story exists (post-v1).
- [Edit flow re-sends compiled bundle text as `source`, not original TypeScript — D7] → harmless against the stub (never inspects `app.source`); flagged as a contract note for #11, which is the first consumer that will care. Alternative (track a `source.ts` artifact now) rejected: no writer of real TS source exists before #11's real pipeline; premature plumbing for data nothing produces yet.
- [Silent fork-on-continuation surprises a user who didn't realize they'd rewound] → out of this change's control by design (decision #52 D2 already settled "no question asked"); the resulting new tile is visible immediately on Home with the same fork provenance label (`forkedFromLabel`) every other fork gets, so it's discoverable after the fact even though not asked about beforehand.
- [SSE parse failures mid-stream] → surfaced as the same honest failure screen (`GenerationClientError{kind:'stream_parse'}` maps to a generic reason string), never a crash; consistent with the existing launch-failure-ui precedent (`HostState.launchFailed`) of turning structured errors into product copy.
- [Token/diagnostic leakage risk] → enforced by construction: `GeneratingScreen`'s props never carry `token.text` or `diagnostic.kind/symbol`, only the current `stage`; `FailureScreen`'s props carry only `diagnostic.hint` strings. Nothing downstream can accidentally render raw internals because they're never passed down.

## Migration Plan

Purely additive: new modules, new screens, two new `StoreAccess` methods, one extended `InstallSpec` field, four new `Screen` variants, new Settings/action-sheet entries, new copy. No changes to `@whim/contract`, `@whim/server`, the version-store on-disk format, or any existing `StoreAccess` method's signature/behavior. Rollback = revert the change's commits.

## Open Questions

- None blocking. D7's compiled-bundle-as-`source` limitation is recorded as a roadmap contract note for #11 rather than resolved here, per this change's explicit non-goal of touching the wire contract or pipeline semantics.
