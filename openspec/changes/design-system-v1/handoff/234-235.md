# Fix piece 234-235: drag commit haptic = drag commit (#234 sheets, #235 orb)

## The rule (one latch per gesture, `Sheet.tsx` `DragCommit` / `startCommit` / `stepCommit` / `releaseCommit`)
- Each frame asks the existing question, "does this frame's projected end pass the threshold?"
  (`releaseCommits` for sheets, `orbReleaseX(...) !== rest` for the orb). That still arms the commit.
- **Arm** on a frame that passes once the drag has moved on ≥ 10 pt (the slop) from its nearest point; the commit haptic
  plays on that frame. **Disarm** only when the drag comes back > 10 pt from its furthest point. A pause or a slower finger
  keeps the commit, and tremor never flips it (one play per real crossing).
- **Release** goes by the latch, not by re-asking with the release velocity: armed → commits unless the release velocity
  points back (projects back > 10 pt, ≈ 20 pt/s); unarmed → commits only if the release frame itself passes, and then
  the haptic plays on that release frame. So the haptic marks the dismissal both ways: a release after it dismisses,
  a release with no haptic never does. The one exception is a deliberate flick back on release (rule 6).
- Root cause of #234: the live check used per-frame velocity, the release used the release velocity. A finger that
  slowed before lifting had felt the haptic at the velocity-projected point, then needed position > half to dismiss.
  Root cause of #235: `orbReleaseX`'s "velocity points back" clause flipped on every tremor frame past the middle.

## Doc wording (system.md §4.3 rule 6; LANDED on this branch at the orchestrator's request; M11/M16 rows unchanged)
The bold sentence now reads: "**A gesture commits on the frame its projected end passes the threshold, and stays
committed until it comes back past the 10 pt slop or the release velocity points back; the commit haptic plays on
that frame, so letting go after it commits and letting go without it never does.** Position alone never commits."
