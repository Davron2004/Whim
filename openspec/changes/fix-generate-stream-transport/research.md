## Current behavior
`generation-client.ts` exports `ClientOptions`, `GenerationClientError`(+`GenerationClientErrorKind`), `rewritePrompt`, `generateApp`; `openGenerateStream`/`httpErrorFrom`/`parseSseBlock`/`readNext` are module-private. `generateApp` calls the injected/global `fetch`, checks `response.body` (line 290: `if (!response.body) throw new GenerationClientError('network', {hint:'Response has no body'})`), then does `response.body.getReader()` and loop-reads raw `Uint8Array` chunks, decoding the accumulated byte buffer non-streaming each time and splitting on `\n\n` (spike-style: never partial-decodes to avoid Hermes's unverified streaming-`TextDecoder`). `rewritePrompt` is unary JSON, no streaming — unaffected by the bug.

`ClientOptions.fetchImpl?: typeof fetch` is the sole injection point already present (doc comment line 17-18: "so `launcher:test` can supply canned `Response` objects"). `LauncherRoot.tsx:185-188` builds `ClientOptions` from `serverUrl` (`loadServerUrl(kv)`, user-entered LAN address via Settings) and `deviceId` (`getDeviceId(kv)`); `fetchImpl` is never overridden on-device — it falls back to global `fetch` at generation-client.ts:271/211.

`LauncherRoot.tsx:272-274` creates one `AbortController` per generation, stored in `genRef.current = {controller, cancelled}`; both `GeneratingScreen`'s Cancel button and hardware back call `onCancelGeneration` (line 326), which sets `cancelled=true` and calls `controller.abort()`. The abort signal is passed into `generateApp(clientOptions, request, controller.signal)` (line 283) and threaded into `fetchImpl`'s `RequestInit.signal`.

`httpErrorFrom` classifies non-2xx bodies into `kind:'device_id'` (matches `DeviceIdError` shape) or `kind:'http'`. `errorReason()` in `LauncherRoot.tsx:118-123` reduces any thrown error to `{reason, diagnostics:[]}`, using `err.hint` only if `err instanceof GenerationClientError && err.hint` — `kind`/`status` are never rendered, matching `FailureScreen`'s "HINT-ONLY BY CONSTRUCTION" contract (`FailureScreenProps.diagnostics: readonly {hint:string}[]`).

## Constraints and invariants
- Decision to cite: none exists yet for this specific fix — this is new territory (RN fetch has no streaming body on-device); the closest governing artifact is `contract/src/index.ts:8-11`'s "Transport notes" comment, which is **incorrect as written** and should be corrected/superseded, likely warranting a new numbered decision (#58) per repo convention (every prior transport/runtime call is logged in `docs/decisions.md`).
- `generation-client.ts:139-153`'s `declare global { interface ResponseBodyReader { read(): Promise<{done, value?}> } interface Body { readonly body: {getReader():ResponseBodyReader}|null } }` is the exact seam a new transport must satisfy — `openGenerateStream`'s return type is `Promise<ResponseBodyReader | 'aborted'>`. Any XHR-backed implementation must produce something conforming to `ResponseBodyReader.read()`'s exact shape so `generateApp`'s byte-buffering/decode loop (lines 354-378) is untouched.
- `GenerationClientErrorKind` (`'network'|'device_id'|'http'|'stream_parse'`) and `GenerationClientError`'s `{kind,status?,hint?}` fields are the UI-facing error contract (`FailureScreen`, `errorReason()`); a transport swap must preserve which kind each failure mode maps to (abort ≠ throw, non-2xx ≠ network, etc.) since `LauncherRoot.tsx`'s downstream logic pattern-matches on these.
- Abort semantics are load-bearing: `generateApp`'s doc comment (line 334) — "An aborted stream ends the iteration silently — no terminal event, no throw" — and `openspec/changes/prompt-flow-ux/specs/prompt-flow/spec.md:65-70`'s "Leaving generation cancels the in-flight request cleanly" requirement (SHALL abort, no install/update). Any XHR transport must translate `AbortSignal` → `xhr.abort()` and surface the same `'aborted'` sentinel `readNext`/`openGenerateStream` already use.
- The SSE framing itself (`event:`/`data:`/`id:`/blank-line, keepalive `: ...` comments) is defined server-side by `server/src/sse.ts:17-21` and consumed by `parseSseBlock` — unaffected by the transport swap; the new transport only needs to deliver raw bytes/text incrementally, not re-parse frames.
- `contract/src/index.ts:1-19`'s "Transport notes" doc comment explicitly states "RN's fetch streams responses, which is the only first-party client" — this is the artifact whose premise BACKGROUND says is false; a delta spec/decision should correct it, not silently leave it standing.
- `GenerationClientError` is a first-party `Error` subclass (`name='GenerationClientError'`) — must stay identical for `err instanceof GenerationClientError` checks in `LauncherRoot.tsx:119` and the test suite's every `catch` block.

## Integration points
- `openGenerateStream` (private, generation-client.ts:266-294) is the natural seam: it currently does `fetchImpl(...)` → `response.body.getReader()`. A parallel XHR-backed path would need to produce the same `ResponseBodyReader | 'aborted'` return value here, likely gated by a capability check (`response.body` undefined) or a `Platform.OS`/env branch — **no existing `.native.ts`/`.android.ts` platform-suffix file or `Platform.OS` branch exists anywhere in `src/host`** (checked, none found), so this repo has no established pattern for platform-conditional launcher modules; the nearest analogous pattern is ambient declare-and-polyfill (`src/host/version-store/env.d.ts`, `text-encoding-polyfill` in `package.json` deps) rather than dual-implementation-file branching.
- `ClientOptions.fetchImpl?: typeof fetch` already exists as the test-injection seam (used by every test in `generation-client.suite.ts`) — a real transport swap must keep this hook meaningful for Node tests (which use Node's native streaming `fetch`/`Response`/`ReadableStream`, all of which DO stream under Node — the suite would need no changes if the fix is scoped to `openGenerateStream`'s fallback behavior only, i.e., new code activates only when `response.body` is absent).
- `readNext(reader: ResponseBodyReader)` (line 300) and the `generateApp` generator (line 344) are downstream consumers that must remain untouched if the new transport's reader conforms to `ResponseBodyReader`.
- Callers: `LauncherRoot.tsx:260` (`rewritePrompt`) and `:283` (`generateApp`) are the only two call sites in the entire repo (confirmed via grep — no other importer of `generation-client.ts`'s exports besides its own test suite).

## Risks and unknowns
- I did not verify whether RN 0.85.3's XHR implementation (also `whatwg`-adjacent, native `XMLHttpRequest` on Hermes) supports `onprogress`/`responseType:'text'` incremental delivery on Android in this RN version — that's an on-device runtime fact outside what static code reading can confirm.
- I did not find any existing XHR usage or XHR mocking anywhere in `src/host` or its tests — there is no prior-art pattern in this repo to model the new transport on; it would be net-new.
- `openspec/changes/prompt-flow-ux/` is **not archived** (its `specs/` deltas sit in `openspec/changes/`, not `openspec/specs/`) despite decision #53 saying "BUILT" — I could not determine whether this is intentional (some other spec absorbed it, e.g. `app-launcher`) or an outstanding archiving gap; flag to the planner since a delta spec for this change would normally target `openspec/specs/app-launcher/spec.md`, but the requirements it must not break currently live only in the un-archived `prompt-flow-ux` change folder.
- I did not check `server/src/routes/rewrite.ts` (unary JSON, presumably unaffected) or `server/src/routes/usage.ts` — out of scope for a streaming-transport fix but flagged as unread.
- `Response.prototype.body` being `undefined` on-device vs. present under Node test — I did not independently re-verify this device fact (per instructions, it's given background), only confirmed the code's `if (!response.body)` guard at generation-client.ts:290 matches the claim.
