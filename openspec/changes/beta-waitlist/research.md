## Current behavior
**Site serving (Q1).** Pages are NOT served by the Hono app/`server/src/app.ts` at all. `server/site.mjs` bundles `server/src/site/build.ts` and runs `buildSite()`, which renders every page in `deploy/site/*.html` into a plain static output directory (temp-dir render, atomic rename into `outDir`). That directory is what Caddy serves read-only for `WHIM_WEB_HOST` (default `whim.anycognition.ca`) — a completely separate site block from the API (`WHIM_API_HOST`, `api.<WEB_HOST>`). The pages site "SHALL NOT reverse-proxy... or keep an access log" and serves no script, CSP `default-src 'none'` (server-deployment spec, lines 114-125). Legal pages (`privacy.html`/`terms.html`/`fr/*`) go through `renderLegalSite` (legal-pages.ts), which reads `deploy/site/legal-identity.json` and refuses the whole build on any finding (missing/invalid identity field, stale retention period vs. server config, dropped consent-disclosure string, draft marker). Non-legal pages (`support.html`, `app-link.html`, `not-found.html`, `privacy-v1.html`) go through the simpler `renderPage`/`template.ts` engine with a **closed placeholder set**: `{{WHIM_SUPPORT_EMAIL}}` (required), `{{WHIM_APP_STORE_URL}}`/`{{WHIM_PLAY_STORE_URL}}` (optional), plus `<!--IF:NAME&NAME2-->…<!--ENDIF-->` blocks and `<!--EACH:LIST:lang-->…<!--ENDEACH-->` (legal pages only, for the provider table). An unknown placeholder or a leftover `{{`/`<!--` marker throws and fails the whole site build (fail-closed). There is currently no route `/beta` and no form anywhere on the site — this is new territory, not an existing page being extended.

**Server framework (Q2).** `createApp()` (server/src/app.ts) builds one Hono app. Routes: `GET /healthz`, `GET /healthz/sse` (anonymous, own tiny slot pool, outside `/v1`), then everything under `/v1/*` behind three stacked middlewares in fixed order: `assignRequestId` → device-identity gate (`shapeOnlyVerifier`, requires `x-whim-device: <uuid>`) → `readEnvelope` (request-envelope headers) → `minimumBuildGate`. Each `/v1/<name>` route is mounted via `app.route('/v1/<name>', make<Name>Route(...))`. **A public waitlist POST must NOT go under `/v1`** (that prefix is contractually device-gated by construction — comment at app.ts:16-20 says a route added later under `/v1` is gated "by construction rather than by whoever remembers"); it would need to be a new anonymous route registered the way `/healthz`/`/healthz/sse` are (`app.get`/`app.post` directly on the root app, outside `/v1/*`), or a wholly separate small service. Today there is no anonymous *POST* route at all — `/healthz`/`/healthz/sse` are both GET.

**Persistence (Q3).** No Postgres; everything is `node:sqlite` (`DatabaseSync`) file-backed under `WHIM_DATA_DIR`, one file per concern: `usage.db` (ledger/admission), `reports.db` (user reports — `NodeSqliteReportStore`, WAL + `PRAGMA secure_delete = ON` + `busy_timeout=5000`). `reports.ts` is the closest template for a new "own SQLite file" store: schema created inline with `CREATE TABLE IF NOT EXISTS`, an `InMemoryReportStore` twin for tests implementing the same interface, a scheduled purge (`schedulePurge`, boot + hourly, unref'd timer, swallows purge errors). Deployment: `WHIM_DATA_DIR` is bind-mounted from a GCP persistent disk; `deploy/provision.sh` sets up a **daily snapshot schedule** (`whim-data-daily`, 07:00 UTC) as the only backup mechanism (docs/deploy.md:44-63) — no logical/SQL dump backup exists. Migrations: none — schema is `CREATE TABLE IF NOT EXISTS`, additive by convention (no migration framework).

**Abuse controls (Q4).** `hono/body-limit` per-route (`config.maxBodyBytesReport` etc., env-overridable `WHIM_MAX_BODY_BYTES_*`), plus explicit byte-length checks against `config.maxPromptBytes`/`maxReportSourceBytes`. Rate limiting is a hand-rolled `SlotController` (in-memory, per-process) with `SlotKind` = `generate`/`unary`/`probe`, keyed by device id where relevant — this is concurrency-slot limiting, not a token-bucket/IP rate limiter; there is also a per-device-per-day + global-per-day counter via `usageStore.admit(...)` (`config.limitReportsPerDeviceDay`/`limitReportsPerDay`), keyed by **device id**, not IP — a public web form has no device id, so this exact mechanism doesn't transfer as-is. Logging: the ONE pino logger (`server/src/logger.ts`) redacts a fixed field-name list (`prompt`, `source`, `deviceId`, `apiKey`, `authorization`, etc., all case variants, up to 3 levels deep) at the serializer, not by convention — **`email` is not currently in `SENSITIVE_FIELD_NAMES`**, so a new route logging a submitted email verbatim (e.g. in an error/refusal log) would not be auto-redacted; the pattern used elsewhere is to log only sizes/ids/codes, never raw user text (see report.ts: logs `reportId, reason, promptBytes, sourceBytes`, never the note/prompt/source itself).

**Privacy/legal statements at risk (Q5).** `deploy/site/privacy.html` states explicitly, twice, "We don't know who you are" (lines ~180, ~194) and "Whim has no accounts... no sharing between users," and frames the whole site under one policy: "This policy covers the Whim app and Whim's website, whim.anycognition.ca, including the app-link pages" (line 40). A `/beta` email-collection form is a **new disclosure category** this policy doesn't cover yet (it currently enumerates only: request-material, phone-id, error-details, app-integrity, connection-logs, reports, usage-records — via `contract/src/disclosure-manifest.ts`'s `MANIFESTS`, gated by `policyManifestFindings` in legal-pages.ts). No CASL, opt-out, or "future updates" language exists anywhere in docs/ or deploy/site today (`docs/legal/change-process.md` never mentions CASL/marketing consent). The `consent-practices.ts` "own opt-in" doctrine (docs/legal/change-process.md line 61) is the closest existing precedent: "a new optional category that keeps every core promise and sends nothing before the user acts is added ... with its own consent path; the main [app] consent version doesn't move." A waitlist page's own consent/opt-out line is analogous but is a **website** disclosure, outside the `ai-data-consent` screen and its fast-gate tripwire (server-deployment spec lines 173-186, `legal-pages.ts` `currentKeepFindings`) — I did not verify whether that tripwire's `data-category`/`data-keep` mechanism is meant to extend to a non-privacy.html page like `/beta`, or whether the beta page needs its own standalone short notice instead.

**Tests (Q6).** Test suites run via `npm run server:test` (server/test/run.mjs bundles + runs Node test files). Site-specific coverage would sit alongside the existing site suites (I did not enumerate them individually here — grep for `server/test/*.suite.ts` matching `site`/`legal`/`template`); `server/test/admission.suite.ts` and `server/test/reports.suite.ts` are the nearest behavioral precedents for a new form-submission route (admission ordering + store round-trip). A new anonymous route would need: a route-level Hono/Node test hitting `createApp()` (or a new small app) directly, a store round-trip test analogous to `reports.suite.ts`, and (if the page is templated) a `renderPage`/`renderTemplate` unit test analogous to whatever exists for `support.html`/`app-link.html`.

**Brand (Q7).** Canonical brand file `release/assets/brand.json`: `iconBackground: "#3f3d8f"` (indigo), `launchBackground: "#fbfaf8"` (paper/off-white). The demo title slide (title-slide.py:38-39) uses the same two colors as named constants `INDIGO`, `PAPER`, citing `release/assets/brand.json` and `icon-foreground.svg` as source of truth. Fonts used in the demo lockup: `InstrumentSans-SemiBold.ttf` (wordmark "Whim", QR label) and `Newsreader-Italic.ttf` (tagline "Small apps you describe."), loaded from `assets/fonts/` — I did not verify these font files/licenses exist in the main Whim repo; they may be demo-repo-only assets. The mini-app SDK's own font token (`src/sdk/tokens.ts:39`) is `system-ui, -apple-system, sans-serif` (CSP forbids remote fonts) — for in-sandbox mini-app UI, not brand pages. The title-slide script (line 11) already anticipates the `/beta`-shaped QR URL, pointed at a placeholder domain.

**OpenSpec schema (Q8).** Only two schemas exist: `whim-harness` and `whim-fixloop`. `whim-harness.apply.requires: [tasks, chains]` — chains.md is mandatory for every whim-harness change regardless of size. A single-agent-sized change still needs a `chains.md`, with one chain covering all tasks. Recent example: `openspec/changes/archive/2026-09-24-request-envelope/`.

## Constraints and invariants
- Every `/v1/*` route is gated by `x-whim-device` "by construction" (capabilities.md line 24, app.ts:16-20) — a public waitlist route must live outside `/v1`.
- The pages site (Caddy) "SHALL NOT reverse-proxy... or keep an access log" and serves static files only (server-deployment spec lines 114-125) — a form POST target cannot be served from that static directory; it needs to hit the API host/Hono app.
- `server-deployment`, `request-envelope`, `content-reports`, `server-admission-control` specs are not present under `openspec/specs/` — the live delta text sits in the still-open `openspec/changes/public-generation-server/specs/*/spec.md`. I did not verify whether this is a stale index or an in-progress archival.
- Decision #33 ("no content in logs") has exactly one deliberate exception (content-reports, capabilities.md line 30) — a waitlist route logging emails would be a second exception unless emails are kept out of logs entirely.
- Site build is fail-closed on any unknown/missing placeholder (template.ts) — a new `/beta` page must declare any new deploy-time value through the closed `PlaceholderName` set in `server/src/site/build.ts`.
- No CASL-specific guidance exists in this repo; the consent/opt-out line's specifics are a product decision, not a legal-review gate.

## Integration points
- New anonymous route alongside `app.get('/healthz', ...)` in `server/src/app.ts`, explicitly outside `/v1/*`.
- New store modeled on `server/src/reports/store.ts` (own SQLite file under `WHIM_DATA_DIR`, in-memory twin).
- New page `deploy/site/beta.html` via `renderPage`/`template.ts`, added to `DEPLOY_VALUE_PAGES` in `server/src/site/build.ts` if it needs a deploy-time placeholder (e.g. the API host the form POSTs to).
- New `config.ts` entries for body cap and a limiter; existing admission is device-id-keyed, so an IP- or global-keyed limiter is new code.
- Privacy: a short notice on `beta.html`, and/or an addition to `privacy.html`'s scope and category tables if the legal-pages gate covers it.
