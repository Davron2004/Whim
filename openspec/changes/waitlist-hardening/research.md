## Current behavior
1. Route. `POST /beta/signup` is mounted on the root app at `app.ts:315`, outside `/v1`, with no device header. The only middleware is `assignRequestId`, then `bodyLimit` (`WHIM_MAX_BODY_BYTES_BETA`, default 4096). Every answer is a 303. Content type: the check is `startsWith('application/x-www-form-urlencoded')`, case-insensitive. Anything else gets `invalid`, then retry (`beta-signup.ts:98-100`).
- Hosts: the page is on `whim-site` (the pages host, `WHIM_WEB_HOST`) and the form action is `https://<WHIM_API_HOST>/beta/signup` on `whim-server`. That is a cross-origin POST, with no proxying. Redirects go to `config.webOrigin` (`WHIM_WEB_ORIGIN`, a bare https origin, required in production) plus `/beta/thanks` or `/beta/retry`.
- Origin and Referer: I grepped `server/src` for `origin`, `cors` and `referer` and found no read of either. The only hits were the `webOrigin` redirect targets, so there is no CORS middleware. I did not read `deploy/cloudrun/Caddyfile`.
- Order of checks: body cap (retry), content type (retry), `hp_ref` non-empty (thanks, nothing stored), `readForm` (retry), limiter (retry), `store.upsert` (thanks). A store throw logs `error` and redirects to retry. `readForm` trims the email and requires platform in `ios|android|other`. `updates_opt_out` must be absent or exactly `'1'`, otherwise invalid.
- Limits: `WHIM_BETA_LIMIT_PER_CLIENT_HOUR` (default 10, sliding hour) and `WHIM_BETA_LIMIT_PER_DAY` (default 2000, UTC day). The key is the sha256 of a per-process salt plus `x-forwarded-for`, held in memory. A missing header shares one key. The limiter is checked only after validation passes.
- Email rule, `isValidSignupEmail` (`beta-signup.ts:41-48`): at most 254 UTF-8 bytes; exactly one `@`, not at position 0; local part matches `[A-Za-z0-9.!#$%&'*+/=?^_`{|}~-]+` and must NOT match `^[=+\-@|%]`; the domain is split on `.` and needs at least 2 labels, each `[A-Za-z0-9](?:[A-Za-z0-9-]{0,61}[A-Za-z0-9])?`. Normaliser: `normalizeEmail` is trim plus lowercase (`store.ts:32`).
- Log lines, all `scope:'beta-signup'`, message `'beta signup'`, info level unless noted: the body-cap handler logs `{scope, outcome:'limited'}`; the rest log `{outcome}` with the request id from the child logger; outcomes are `stored|updated|invalid|limited|trap|error`; `error` is logged at error level and also carries `errorClass` (constructor name or `typeof`) (`beta-signup.ts:110`); the logger redacts any field named `email`.

2. Stores. Interface (`store.ts:64-75`): `upsert(signup: WaitlistSignup): Promise<UpsertOutcome>`, `export(filter?: WaitlistFilter): Promise<WaitlistRow[]>`, `remove(email: string): Promise<boolean>`, `purge(now: number): Promise<number>`, `close(): Promise<void>`. `WaitlistSignup` is `{email, platform, updatesOptOut, noticeId, now}`. `WaitlistRow` is `{email, platform, updatesOptOut, noticeId, createdAt, updatedAt}`.
- SQLite: file `WHIM_DATA_DIR/waitlist.db`, table `waitlist`, primary key `email` (normalised), WAL with `secure_delete`, index on `updated_at`. The upsert is `ON CONFLICT DO UPDATE` setting platform, `updates_opt_out = excluded.updates_opt_out`, `notice_id` and `updated_at`, and keeping `created_at` (`store.ts:207-211`). It does a prior SELECT to report `stored` or `updated`.
- Firestore: collection `waitlist`, doc id is the hex sha256 of the normalised email, and the `email` field is kept for export. The upsert runs in a transaction. An existing doc gets `tx.update` of `{platform, updatesOptOut, noticeId, updatedAt}`, so the opt-out is overwritten the same way. A new doc gets `tx.create` with `createdAt`. `remove` is a transactional delete, `export` reads the whole collection, and `purge` uses `deleteInBatches` on `where updatedAt < cutoff`.
- In-memory: a Map keyed by the normalised email, with the same overwrite semantics.
- Notice id: `CURRENT_NOTICE_ID` ('beta-1') is stored on every upsert and replaced on re-signup. `NOTICES` is append-only. Retention: `WAITLIST_RETENTION_DAYS = 730`, purge cutoff `now - 730 days` against `updated_at`, strict `<`. The purge runs at boot and hourly, and `whim-admin purge` runs it with the `waitlist:` line.

3. Operator. `whim-waitlist` / `node server/waitlist.mjs` has two commands: `export [--platform …] [--updates-ok]` and `remove <email>`. `remove` is a hard delete and nothing is kept. It exits 1 with "is not on the list" when the email is absent. The CSV columns are email, platform, updates_opt_out, created_at, updated_at (ISO). `csvCell` only quotes cells containing `" , \r \n`. There is no formula-injection handling in the CLI. Instead the route rejects a local part starting `= + - @ | %`. There is no waitlist list or import command. `whim-admin import-sqlite` copies rows from `waitlist.db` into Firestore under `waitlistDocId`, and `docs/deploy.md` says a `createdAt` collision keeps the earlier one. An import would carry `updates_opt_out` as stored (I did not read `copyInto`).

4. Tests and spec scenarios. Suites are `beta-signup.suite.ts`, `waitlist.suite.ts`, `beta-site.suite.ts`, `store-conformance.suite.ts` (cases `waitlistRows`, `waitlistConcurrentSignups`, and the purge case), `import-sqlite.suite.ts` and `admin-purge.suite.ts`. Run them via `npm run server:test` (`server/test/run.mjs`). I did not verify that `run.mjs` lists them; `acceptance.ts` imports `waitlist.suite`, `beta-signup.suite` and `beta-site.suite`. `npm run stores:firestore:test` (`scripts/firestore-emulator-test.mjs`) runs the Firestore emulator. `firestore-conformance.ts` and `firestore-import.ts` exist. I did not read the emulator script.
- Conformance case `waitlistRows` re-signs `Person@Example.COM` as ios with opt-out true and `noticeId` 'notice-2', and expects `updated`. That is the overwrite behaviour #109 would change. `beta-signup.suite.ts:90,93` assert that `person@localhost` and `=HYPERLINK(1)@example.com` are refused.
- beta-waitlist requirement "One row per person" says "a repeat signup SHALL update platform, `updates_opt_out`, notice id and `updated_at` while keeping `created_at`". Its scenario "Repeat signup updates" expects `updates_opt_out` true after the second post ticks it; it never covers a re-post with the box unticked. That requirement and scenario, and the server-storage-backends scenario "Repeat waitlist signup on Firestore", are what a sticky opt-out touches. "Retention and operator access" scenario "Removal": "its row is gone and a later export omits it". This contradicts a suppression list unless it is read as the export only. Nothing in the spec mentions Origin or Referer.

5. #111 spec text. "Signup route": "A valid submission (a syntactically valid email of at most 254 bytes and a platform in `ios|android|other`) SHALL be stored…"; the code adds the formula-lead and dotted-domain rules; "Any other submission SHALL be redirected to retry", so those are retry-with-no-reason. "Emails never logged": "signup log lines SHALL carry only an outcome code and a request id"; the `error` line adds `errorClass`. "Consent wording is recorded": "The site build MUST fail when the normalized text … does not hash to a registered notice id"; `signupNoticeFindings` also fails when the id is registered but is not `CURRENT_NOTICE_ID` (`notice-check.ts:46-48`).

6. Firestore files. `deploy/firestore/indexes.json` has only a `requests` collection-group index and nothing for `waitlist`. The purge `where updatedAt <` is a single-field query. The `FirestoreRoot` prefix is used by `this.root.collection(...)`.

## Constraints and invariants
- Never log email, platform or client address (spec "Emails never logged"); the site suite holds the policy's retention to `WAITLIST_RETENTION_DAYS`. The three backends must pass one conformance suite, so interface changes land in memory, SQLite and Firestore together. `NOTICES` is append-only. Any privacy-policy change is checked by legal-pages checks in both languages. The AI-consent version must not change. The Firestore doc id is a hash of the normalised email, and the SQLite key is the normalised email, so `remove` leaves no tombstone on either backend.

## Integration points
- `beta-signup.ts` handler between content-type and `readForm` (headers are available via `c.req.header`). `WaitlistStore` and its three implementations, the conformance suite, `import-sqlite.ts` and `purge.ts`. `cli.ts` `removeRow` and `csvCell`. `config.webOrigin` is the pages origin, already in `BetaSignupDeps.config`.
