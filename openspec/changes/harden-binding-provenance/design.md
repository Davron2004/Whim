## Context

`invariants/sandbox-isolation/bridge/runner.mjs:72` calls `page.exposeFunction('whimHostDispatch', host.dispatch)` with no frame-provenance guard. `exposeFunction` installs the binding on the global of every execution context in the page — including the opaque-origin sandboxed `srcdoc` iframe — and discards the `{context,page,frame}` source, so any hostile bundle running in the sandbox can call `globalThis.whimHostDispatch(frame)` directly and get an authoritative sysret from the real `Dispatcher.handle` over a real `:memory:` engine (research.md "The bug: an unguarded host binding in the bridge invariants suite").

This is test-harness code, not product code: decision #28 (`invariants/` is owner-authored, its non-vacuity load-bearing) and decision #41 (bridge syscall authority is `ev.source === window.parent`, never a nonce) both bound what "fixing" this means — the guard is an *additional necessary condition for the test to be sound*, not a change to the product's own authority rule (research.md "Constraints and invariants"). The parent change (`harden-synthrun-binding-isolation`) already shipped the correct pattern twice, at `synthrun/observe.ts:492-502` and `synthrun/capability.ts:145,153-154` (research.md "The proven fix pattern from the parent change"); this change closes the one site the parent change's own research missed and adds the standing check that would have caught it.

## Goals / Non-Goals

**Goals:**
- Close `runner.mjs:72` with a first-statement frame-provenance guard, behaviour-preserving for every existing scenario.
- Add a structural AST check under `checks/` that converts the current one-time pattern census (research.md "Pattern census: every Playwright host binding in the repo") into a standing, gate-enforced property, reachable via `npm run checks:test` with zero edit to `scripts/gate.sh`.
- Make the guard's refusal observable (a counter), not a silent no-op, so the adversarial scenario cannot pass vacuously.
- Record, in this document, the process failure that let the same line survive three prior research passes (research.md "How the research primitive failed across three runs"), and name the concrete artifact requirement that fixes it.

**Non-Goals:**
- A shared `exposeMainFrameBinding` helper — rejected as a trust inversion (Decision 2).
- A name-scrub/`addInitScript` defence — not the guarantee (Decision 4); Playwright's `Runtime.addBinding` call carries no scoping params, so the raw binding always lands on every context regardless of what the sandbox realm's global is later scrubbed to.
- Closing the gap that `scripts/gate.sh` is Class-2-protected while the suites it runs (including `checks:test`) are not (Open observation) — pre-existing, true of every Node suite in the gate, not this change's job.
- Any change to bridge syscall authority (decision #41) or to the nonce-authenticated verdict mechanism (spike2 §3, finding F4) — unrelated and must not be conflated with this guard (research.md "Constraints and invariants").

## Decisions

### D1 — the detector is a structural AST check under `checks/`, but it is a NEW sibling module, not a `Pass` registered in `checks/index.ts`'s `PASSES` array

**Rejected alternative 1: an ESLint `no-restricted-syntax` selector.** `.eslintignore` lists `invariants/` (also `fixtures/adversarial/`, `src/runtime/web/`, `build/generated/`) deliberately, because those are adversarial fixtures that reach for forbidden globals on purpose (research.md "Existing detection: none, and ESLint is structurally blind"). A rule there provably could never see `runner.mjs:72` — the one vulnerable file. False assurance, worse than no check.

**Rejected alternative 2 — flagged correction, not a silent improvement: register the new pass in `checks/index.ts`'s `PASSES` array and reach it through `runStaticChecks(source)`.** This was the working assumption going into this document and it does not survive contact with the code. `checks/index.ts:37-48`'s `runStaticChecks(source, opts)` is scoped to exactly **one already-parsed mini-app bundle source string**: it calls `parseSource` once (`checks/internal/parse.ts:37-44`, which hardcodes `ts.ScriptKind.TSX` because, per its own comment, "the bundle contract … is one TS file with classic JSX"), builds one `CheckContext` (`checks/index.ts:44`), and runs each `Pass` — typed `(ctx: CheckContext) => void` (`checks/internal/scope.ts:29`) — over that single context. There is no file-system walking anywhere in this pipeline; it exists to score one LLM-generated candidate bundle against the vc-sdk contract (the generation server's per-candidate gate), not to audit the repo's own source tree. Concretely: feeding `runner.mjs` or `synthrun/observe.ts` through it as `source` would draw `disallowed_import` from `importAllowlistPass` (`checks/index.ts:28`, req "Imports resolve only to vc-sdk") on the file's `playwright`/`node:*` imports before a binding-provenance question is ever reached. Registering there is the wrong domain — the same category of failure as the rejected ESLint alternative, just one layer deeper.

**What `checks/test/hostile/` already is, and why it doesn't transfer.** `checks/test/hostile/corpus.ts` is a corpus of hostile *mini-app bundle* sources — each case is a fragment wrapped in a fixed `defineApp` header/footer (`APP_IMPORT`/`APP_TAIL`, `corpus.ts:5-21`) and run through `runStaticChecks`; it is already wired into the harness (`checks/test/acceptance.ts:30` imports `runHostileCorpus`). It validates the mini-app static-check passes, not repository harness code, so it is not "the hostile-fixture directory" this task's read budget anticipated — there is no existing "scan these real repo files" fixture set to reuse, and none needs to be invented: the detector reads the real files directly (below), it doesn't need synthetic fixtures to exercise its positive case.

**Chosen: a new, independent module under `checks/`, wired into the existing `checks:test` seam, not into the bundle-contract pipeline.** The real reachable-from-gate extension point is `checks/test/run.mjs`, and it is more general than `runStaticChecks`: it esbuild-bundles `checks/test/acceptance.ts` and runs the result under Node (`checks/test/run.mjs:12-40`), and `acceptance.ts` is free to import and exercise *any* module under `checks/`, not only `PASSES` members — it already does exactly this for the unrelated `runHostileCorpus` helper. `scripts/gate.sh:63` (`check "static-checks" npm run -s checks:test`) is unchanged either way, so the Class-1 reachability claim in the read-budget brief holds — it is just reached one level up, from `acceptance.ts`, not from `checks/index.ts`. Concretely: a new module (`checks/audit/binding-provenance.ts` — deliberately NOT under `checks/passes/`, because every other member of that directory is a `Pass` registered in `checks/index.ts`'s `PASSES` array and this module is not one; placing it there would invite exactly the mis-registration this decision rejects) that (a) parses each target file with a direct `ts.createSourceFile` call — bypassing `checks/internal/parse.ts`'s TSX-only assumption, selecting `ts.ScriptKind.JS` for `.mjs`/`.js` and `ts.ScriptKind.TS` for `.ts` by extension, since TypeScript's parser accepts plain ESM under `ScriptKind.JS` — (b) walks each file's AST for `exposeFunction(` and `exposeBinding(` call expressions, and (c) for every `exposeBinding` site, checks that the callback's first statement matches one of the two guard shapes from D2. A new `test()` call in `checks/test/acceptance.ts` (or a sibling file also reachable from that same entry point) invokes it and asserts zero violations. Because it rides the *same* esbuild entry point and Node process as the existing suite, it needs no second `run.mjs`/second esbuild invocation, and it inherits `external: ['typescript']` (`checks/test/run.mjs:32`, the "Dynamic require of fs" gotcha) for free rather than needing to redeclare it.

**Scan surface must be structural, not a hardcoded 3-file list.** Per research.md "Risks and unknowns": "What is *not* durable is the sweep itself — it is a one-time claim that rots on the next commit. Workstream A's AST check is what converts it into a standing property." A hardcoded allowlist of `runner.mjs`/`observe.ts`/`capability.ts` would repeat exactly the failure mode this change exists to close — a 4th binding added next quarter would be as invisible to a 3-file list as `runner.mjs:72` was to three research passes. The detector should glob the same tree the manual census swept (research.md "Pattern census…": `scripts/`, `invariants/`, `build/`, `src/`, `server/`, `contract/`, `synthrun/`, `checks/`, excluding `node_modules` and `openspec/changes/archive/**` prose hits already noted as non-code) for `.ts`/`.mjs` files that reference `exposeFunction`/`exposeBinding`, and apply the AST check to every hit — sizing and exact glob roots are an implementation task, not fixed here.

**Implementation gotchas carried over from repo experience, to save the implementing chain a rediscovery:**
- Bundling the `typescript` package into an esbuild Node ESM suite throws `"Dynamic require of \"fs\" is not supported"` when inlined — `external: ['typescript']` is required; already present at `checks/test/run.mjs:32` and inherited as described above.
- `ts.isImportCall` is `@internal` and not on the public `.d.ts` surface; if a later variant of this pass ever needs to recognize dynamic `import(...)`, match `SyntaxKind.ImportKeyword` inside a `CallExpression` instead, not `ts.isImportCall`.

### D2 — inline guards at each call site, not a shared helper

**Rejected alternative: extract `exposeMainFrameBinding(target, name, cb)`** and call it from `synthrun/observe.ts`, `synthrun/capability.ts`, and the invariants runner.

**Rationale for rejection — a trust inversion.** The helper would have to live in an agent-editable location, which makes an agent-editable module load-bearing for Class-2 verification code. An agent edit to the helper could then silently weaken the invariants suite's own guard — precisely the failure decision #28 exists to prevent. Inline guards, plus a structural check that verifies the guard's *shape* at every call site independently, has no such inversion: weakening one site doesn't weaken the others, and the structural check catches a weakening at any of them.

**Cost accepted and named:** three near-identical two-line guards. The structural check (D1) must recognise both forms: the page-level form `source.frame !== page.mainFrame()` and the context-level form `source.frame !== source.page.mainFrame()`.

### D3 — refusal must be observable

A silent `null` return is indistinguishable from a no-op, so an adversarial test asserting only `sysret === null` could pass vacuously. `runner.mjs` gets a refusal counter surfaced on the object `scenario()` returns, mirroring `hostProvenanceRefusals` in `synthrun/observe.ts`. Refusal returns `null` — the dispatcher's own no-result shape — deliberately not an error string, because Playwright's `deliverBindingResult` evaluates the return expression back inside the CALLER's realm. The guard must be the FIRST statement, refusing before `JSON.parse` and before `dispatcher.handle`.

### D4 — a name scrub is not a fix

Playwright calls CDP `Runtime.addBinding` with `{name}` only, never the scoping params, so the raw binding lands on the global of every execution context; `__playwright__binding__controller__` survives in the sandbox realm and can re-mint the name after a `delete`. Defence in depth at best, never the guarantee. If a scrub is ever added, record the ordering trap: `exposeBinding` must precede `addInitScript` (`synthrun/observe.ts:529-538`); reversed, both silently no-op with no type error and no gate failure.

### D5 — the process fix is a census, not a discipline reminder

"Find an exemplar to copy" and "enumerate every occurrence" return the SAME hits, but only the second forces a verdict per row. A census structurally cannot emit "cited the vulnerable line as the good example" — that row would have to read UNSAFE. Cite research.md's section "How the research primitive failed across three runs" for the mechanism: a wrong comparison axis (`page.` vs `context.` exposure scope) while the same document had, thirty lines earlier, already established that `exposeFunction` discards the source; the two facts were never crossed. Compounded by an "owner-authored / out-of-scope" classification applied BEFORE the soundness question, which removed the incentive to ask it. It survived three runs — so a one-off reminder demonstrably does not work; the fix has to change what the artifact is required to CONTAIN. Also record why the sink must be mandated: `openspec/critic/open-follow-ups.md` already exists but has no mandated writer, so the finding survived only as prose and needed a human to hand-carry it into a new run.

### D6 — behaviour-preserving, verified scenario by scenario

Cite research.md "The legitimate call path is already main-frame". Scenarios 1,2,6,7,8 (`runner.mjs:88-101,103-109,215-224,226-235,237-271`) use the normal outer-page relay. Scenario 5 (`runner.mjs:200-213`) calls `globalThis.whimHostDispatch` via a bare `page.evaluate` (`runner.mjs:204-208`), which targets the MAIN frame by default and so passes the guard. Scenarios 3 and 4 (`runner.mjs:111-151,179-198`) evaluate inside `appFrame(page)` but never touch `whimHostDispatch`. Scenario 3b (`runner.mjs:153-177`, A6, `__whimSyscall` non-writable) also evaluates inside `appFrame` but does not call `whimHostDispatch` either, so it is unaffected by the guard.

## Risks / Trade-offs

[A detector that reds the gate cannot pass its own self-gate] → The chain-dispatch loop self-gates every chain before merge, so the detector chain must never be the chain that makes the gate red. Ordering is reversed: a human applies the workstream-B guard first, then the detector chain is dispatched against an already-patched tree and self-gates green. The pre-fix proof is not lost — it is captured against the pinned pre-fix commit 754e2f7 in a scratch worktree, which is strictly better evidence because it stays reproducible instead of being a transient property of one worktree.

[`scripts/gate.sh` is Class-2 protected but the suites it invokes — including `checks:test`, which this change's own detector lives inside — are not, so an agent could weaken this detector after the fact without a Class-2 gate] → Explicitly NOT fixed here. Pre-existing, true of every Node suite in the gate (`checks:test`, `vstore:test`, `storage:test`, `bridge:test`, etc.), consistent with the current trust model recorded elsewhere in the harness. Recorded as an open observation, not solved by this change.

[Three near-duplicated inline guards (D2) invite future copy-paste drift — a fourth site added later might reuse only the `exposeFunction`/`exposeBinding` call shape and forget the guard] → Mitigated structurally, not by discipline: D1's detector is repo-wide and glob-scanned rather than a fixed file list, precisely so a new site is caught by the gate rather than by a future research pass.

[The detector's precondition is "the file imports `playwright`" — a helper that receives a `page`/`context` object passed in from a caller, without importing `playwright` itself, is invisible to it] → Known, accepted limitation of the census-by-import approach; not mitigated by this change.

## Migration Plan

No data migration; this is test-harness and gate-tooling code only, nothing shipped to a device or persisted. Sequencing:
1. A human applies the workstream-B guard (handoff/invariants-binding-guard.md) FIRST, with its own red-check recorded. Only then is the workstream-A detector chain dispatched. Same-batch landing is NOT permissible in the reverse order: the detector must never merge against a tree where the guard is still pending.
2. Record the pre-fix evidence against pinned commit 754e2f7 in a scratch worktree — the detector must flag runner.mjs:72 there. Against the live (post-guard) tree the detector must report zero violations and the chain self-gates green.
3. Confirm the existing bridge-invariants scenarios (1,2,3,3b,4,5,6,7,8) all still pass unmodified, per D6's per-scenario trace — this is the behaviour-preservation check, not a new assertion.
4. No rollback beyond a normal revert: the change touches no runtime/product code path (decision #41's authority rule is untouched), so a revert only re-opens the test-harness hole it closes, it cannot regress product containment.
