# Whim Tier-C Rubric — v1

Tier C is the qualitative judgement layer of the corpus-eval harness (`evals/`, design D7/D8). It
runs only when Tier A has passed for the case (a Tier-A failure short-circuits Tier C, per spec)
and never contributes to the case's pass/fail verdict — it exists to surface *quality* signal a
deterministic gate and a fixed set of behavioral assertions cannot capture.

**Version:** `v1`. Any edit to the scored criteria below (the table between the
`rubric-scored-content` markers) REQUIRES bumping this version identifier and
`evals/rubric/index.ts`'s `RUBRIC_VERSION` + `RUBRIC_CONTENT_HASH` together — an edit to the
scored content without a matching version bump fails `evals/test/tier-c.test.ts` (design D8).

## Human-eyeball protocol

A human reviewer:

1. Loads the candidate mini-app in the sandbox runtime and reads the case's prompt (and, when
   visible, its expectation).
2. Interacts with the app the way an end user described by the prompt would — exercises the
   primary flow, not just the happy path.
3. Scores each criterion below on its 1–5 scale, writing one sentence of rationale that names a
   concrete observation. A bare score with no rationale is never acceptable — Tier C rejects a
   verdict missing a rationale as malformed, never as a pass.
4. Never lets the case's Tier-A or Tier-B result influence a Tier-C score — the three tiers are
   independent signal, not inputs to one another.

An automated (scripted/replay/live) judge follows the same four criteria and the same 1–5 range;
a live judge is prompted with this document's scored section verbatim.

## Scored criteria

<!-- rubric-scored-content:start -->

| id | label | 1 (low) | 5 (high) |
| --- | --- | --- | --- |
| `intent-fidelity` | Intent fidelity | The app does something unrelated to, or contradicts, what the prompt asked for. | The app does exactly what the prompt asked for, including implied requirements the prompt didn't spell out. |
| `usability` | Usability | Controls are unlabeled, confusing, or require guessing to operate. | A first-time user could operate every control without instructions. |
| `robustness` | Robustness | A predictable input (empty state, first launch, a duplicate entry) visibly breaks the app. | Empty states, first launch, and duplicate/edge inputs are all handled gracefully. |
| `polish` | Polish | Looks like an unfinished sketch — misaligned layout, or actions with no visible feedback. | Reads as a small finished app: consistent layout, and every action gives visible feedback. |

<!-- rubric-scored-content:end -->

Each criterion is scored on an integer 1–5 scale (inclusive). A verdict must score every
criterion listed above by its `id` and supply a non-empty rationale for each — a verdict missing
a criterion, missing a rationale, or scoring outside 1–5 is recorded as a Tier-C `error`, never a
passing score (spec "Malformed verdict is an error, not a pass").
