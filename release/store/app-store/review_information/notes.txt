HOW TO TRY WHIM
No login, no account. Home already has example apps.
1. Tap "Describe an app..." on Home.
2. A fresh install opens the AI-data consent screen first -- expected, not a bug. "Agree and continue" proceeds; "Not now" or system back returns to Home with nothing sent, examples still usable.
3. Type a one-line description, tap "Continue"; answer (or skip) up to three clarifying questions, tap "Continue" again.
4. Review the plan, tap "Build it" (about a minute), then "Open it".
5. Inside the app, the floating orb's menu has "Report this app" -- the in-app reporting 4.7.1 asks for.
6. Long-press an installed app's tile, choose "App link", for its universal link as selectable text.

GUIDELINE 4.7
Mini apps are plain HTML5/JavaScript, generated per user request, run in a same-process WebView. Three legs sandbox that: an opaque-origin iframe, a CSP with no unsafe-eval, and host-side neutralization of globals a bundle could reach through. No network API (fetch, XMLHttpRequest, WebSocket, EventSource, navigator.sendBeacon) is exposed to mini-app code, which never sees the host's network stack.

[TODO -- network-deny is not fully shipped yet] Those legs stop a mini app calling out, but not yet the sandboxed frame navigating itself to an arbitrary URL as a top-level navigation, still a GET off the device. A native WebView policy refusing that load class is planned; until it ships, do not tell App Review no data can leave the device from a mini app -- state only what the shipped legs block, and remove this note the day the native leg lands.

4.7.1 filtering/reporting/privacy: the consent screen ("Before Whim makes apps for you") discloses what is sent and to whom before the first request. The server checks a small, bounded content-policy classifier call before running the clarify/rewrite/generate model; a rejected request gets a refusal and that model is never called -- filtering fails closed. Reporting is live from the orb menu, the done step, and each app's history header. Nothing to block: no accounts, no sharing, no way to see another user's content.

4.7.2 no native APIs without permission: a mini app reaches the device only through ten local, asynchronous capability-bridge calls, confined to its own data: storage.kv (get/set/remove), storage.records (append/list/update/remove), diag.echo (a round-trip test pipe, no side effect), cues.haptic, cues.sound. None touches camera, microphone, location, contacts, filesystem, or network.

4.7.3 no data/permissions without consent: a mini app only gets what the user typed into it and what it saved via the calls above -- never the consent grant, device ID, or any host credential.

4.7.4 an index with a universal link per app: the Home grid is that index; each tile's long-press menu has "App link" as selectable text.

4.7.5 age limits: Whim's own content has no descriptors, but user-driven generation gets a 13+ floor, gated by the 4.7.1 policy.

GUIDELINE 2.5.2
Mini apps do not download or execute code that changes Whim's own features. Each is plain HTML5/JS in a WebView with the containment above; none can add, remove or alter Whim itself -- no new screens, no capabilities, nothing running outside its sandboxed frame.

WHAT LEAVES THE PHONE, AND WHEN
Nothing leaves the phone from inside a running mini app -- see the note above for the one open gap. Three things leave the phone, outside any mini app's reach: a generation request (clarify/rewrite/generate), sent only after AI-data consent, carrying what the user typed, their answers, the approved plan, and, for a change to an existing app, its name, code, description and saved-data shape -- never the rows saved inside it -- plus an anonymous per-install device ID for daily limits; a report, sent only when the user taps "Send report", not gated on consent; and a GET /healthz check, sent only once consent is granted, carrying no user content or body. Nothing else: no analytics, no crash reporter, no ads SDK, no background telemetry.
